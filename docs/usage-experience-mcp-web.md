# P&ID-Agent 使用体验反馈：网页编辑、LLM 生成与 MCP 协同

日期：2026-07-16
体验版本：`2.1.0-alpha.1`
体验环境：macOS、Chrome、Ollama `qwen3.6:35b`、P&ID-Agent Web 与 stdio MCP

## 1. 总体感受

P&ID-Agent 当前最有价值的部分不是“能在网页上画几个符号”，而是已经建立了比较清晰的语义底座：设备端口、junction、connector、revision、原子事务、网页编辑器和 MCP 共用同一套文档模型。这使它具备了继续发展为“人工与 Agent 共同编辑结构化 P&ID”的基础，而不只是一个普通 SVG 画板。

这次体验最终成功完成了一张废气冷凝器流程图，包括左右系统接口、入口和出口隔离阀、换热器、四组压力/温度仪表、四个根部阀、四个独立 junction、主工艺管线和冷却空气线路。MCP 语义验收结果为：13 个 symbol、4 个 junction、18 个 connector、7 个 text，共 42 个元素。E-101 的 `tube_in`、`tube_out`、`shell_in`、`shell_out` 均建立了真实端口绑定，每个仪表 junction 均有 3 条连接。

整体评价是：**底层模型方向正确，MCP 能真正完成工程语义编辑，但网页与外部 Agent 的协同体验、错误处理和常用编辑能力还处于明显的 Alpha 阶段。**

## 2. 做得好的地方

### 2.1 语义连接不是“看起来连上了”

connector 可以绑定到具体的 `element_id + port_id`，junction 也有真实的 `node` 端口。这样一条线不仅在视觉上连接设备，Agent 还能继续查询设备、仪表和分支之间的拓扑关系。

这点非常关键。很多轻量绘图工具只能生成线段，后续无法回答“PT-101 接在哪条主管上”“冷却空气连接的是换热器哪一侧”等问题。P&ID-Agent 已经避免了这个根本缺陷。

### 2.2 原子事务适合 Agent 编辑

一次 `apply_transaction` 可以同时添加设备、junction 和 connector，并在整体校验通过后统一写入。失败时不会留下一半设备、一半管线的残缺状态。

revision 乐观并发也很有价值。它能防止 Agent 基于旧图纸覆盖人工刚完成的修改。对于多人或多 Agent 协作，这个能力比单纯的画布功能更重要。

### 2.3 MCP 工具数量少但闭环完整

当前 MCP 已包含：

- `list_documents`
- `create_document`
- `get_scene_summary`
- `get_document`
- `apply_transaction`
- `list_symbols`

通过这些工具，Agent 可以完成“读取符号库 → 读取最新图纸 → 生成事务 → 应用事务 → 重新读取场景验收”的完整闭环。这次绘图就是通过该闭环完成的，没有依赖网页中的 LLM 按钮。

### 2.4 服务端会重新计算真实端口坐标

事务中即使提供了端点坐标，服务端仍会根据符号尺寸、位置和旋转角度重新归一化端口位置。这使我能够把四个根部球阀旋转为 `-90°`，并保持上下端口与仪表支管准确连接。

### 2.5 网页基础布局清楚

左侧符号库、中间画布、右侧 Agent 面板的结构容易理解。符号分类、基础快捷键、撤销/重做和 SVG 导出入口也比较直观。白色背景和默认深色线条适合工程图纸。

## 3. 实际遇到的问题

## P0：MCP 修改后，已打开的网页不会自动更新

MCP 和网页服务确实共用同一个 SQLite 数据库，但网页只在初始化、打开文档或自身完成事务时读取文档，没有轮询、SSE 或 WebSocket。

实际表现是：

1. MCP 已经成功提交事务；
2. MCP 能读到新的 revision 和元素数量；
3. 浏览器仍显示旧 revision 和旧画布；
4. 手动刷新网页后，新内容才出现。

这会产生两个问题：

- 用户容易误以为 MCP 没有生效；
- 用户可能继续在旧 revision 上操作，与 MCP 产生并发冲突。

建议：

- 短期方案：网页每 1～2 秒轮询当前文档 revision；revision 变化时重新获取文档；
- 更完整方案：服务端通过 WebSocket 或 SSE 推送文档变更事件；
- 如果用户正在拖拽或编辑，应先提示“检测到外部修改”，避免直接打断当前操作；
- 页面顶部显示明确状态，例如“已同步至 r24”“检测到外部更新，点击载入”。

验收标准：

- MCP 提交成功后，网页在 2 秒内出现新元素；
- 不需要整页刷新；
- 不丢失当前缩放、平移和选中状态；
- 外部 revision 与本地未提交编辑冲突时有明确提示。

## P0：LLM 超时被显示为笼统的 500

首次在网页中使用 Ollama `qwen3.6:35b` 生成整张图时，页面最终只显示：

```text
Error: 500 Internal Server Error
```

服务端实际错误是 `httpx.ReadTimeout`。该请求约有 5,386 个输入 token，模型在 120 秒内已经生成约 7,065 个 token，但仍未结束。Ollama 本身正常，同一模型的小请求约 2.66 秒即可返回。

当前问题包括：

- Provider 默认超时为 120 秒；
- 请求没有限制最大输出 token；
- 对推理模型没有关闭长思考；
- `httpx.TimeoutException` 没有转换成用户可理解的响应；
- 页面不知道当前处于加载模型、推理、生成 JSON、校验还是应用事务阶段。

建议：

- 捕获连接超时和读取超时，返回 504 或结构化错误；
- 错误信息明确显示模型、Base URL、已等待时间和建议操作；
- 为本地推理模型提供“关闭思考”选项；
- 设置合理的最大输出 token；
- 网页允许设置超时，或提供快速/标准/长任务三档；
- 最好增加阶段状态或流式进度，而不是一直显示“处理中”。

验收标准：

- 超时后页面显示“模型在 120 秒内未完成”，而不是 500；
- 用户可以直接重试、延长超时或关闭思考；
- 超时不会留下部分事务；
- 服务端日志保留底层错误，网页不暴露大段堆栈。

## P1：网页缺少属性面板，很多常规编辑只能通过 MCP 完成

网页可以放置和移动符号，但目前缺少常见的属性编辑能力，例如：

- 修改设备标签；
- 修改符号旋转角度；
- 修改线宽、颜色和虚线；
- 修改 connector 的 process tag；
- 查看 connector 绑定的 source/target；
- 修改文字内容、字号和对齐方式；
- 精确输入坐标和尺寸。

这次四个根部阀必须竖向放置。网页放置符号时固定 `rotation: 0`，因此只能通过 MCP 设置 `rotation: -90`。

建议增加右侧属性检查器。选中不同元素时显示对应字段，并保持修改仍通过原子事务提交。

验收标准：

- 用户可以在网页中把阀门旋转 90°；
- 修改标签不需要删除重建；
- 可以查看一个 connector 是否真正绑定到端口；
- 多选时可批量修改公共样式。

## P1：MCP 的 `transaction_json` 对 Agent 不够友好

`apply_transaction` 当前接收一个 JSON 字符串，而不是结构化对象。虽然功能可用，但存在几个体验问题：

- MCP 客户端看到的是一个不透明字符串，难以利用工具参数 schema 自动校验；
- Agent 需要先序列化一遍 JSON，再把它塞进另一个 JSON 参数；
- 出错时不容易快速定位是第几个 operation、哪个字段或哪个端口；
- 大事务在日志和调试界面中可读性较差。

建议：

- 让 `apply_transaction` 直接接收结构化 transaction 对象；
- 增加 `validate_transaction`，只校验但不写入；
- 错误返回 operation index、element id、字段路径和建议值；
- 可增加 `get_transaction_schema`，让 MCP 客户端明确获得当前版本 schema；
- 对高频动作可增加少量便捷工具，但仍由服务层转换成同一事务模型。

## P1：换热器图例难以同时满足两侧介质的直观布线

当前通用换热器有四个真实端口：

- `tube_in`：左上
- `tube_out`：右下
- `shell_in`：上部
- `shell_out`：下部

主工艺从左到右连接管程没有问题，但如果冷却空气要求在设备下方从右向左流动，同时又必须使用真实壳程端口，就需要从右下方绕到设备顶部的 `shell_in`。这会跨越主工艺管线，视觉上容易被误解为连接点。

建议：

- 增加不同朝向的换热器/冷凝器图例；
- 允许图例声明多个可选端口布局；
- connector 交叉处支持 line jump/跨线桥；
- 交叉但不连接时提供明显的视觉语义；
- 增加更贴近冷凝器的专用符号，而不只使用通用换热器。

## P1：connector 没有正式流向显示

当前 connector 具备 source/target 语义，但画布没有原生箭头。为了让人看懂方向，只能添加独立文字“→”和“←”。这能表达方向，但文字与管线是分离元素，移动管线时不会自动跟随。

建议为 connector 增加可选的流向箭头属性，例如：

- `flow_direction: forward | reverse | none`
- `arrow_position: start | middle | end`

箭头应根据 connector 路径自动渲染，并在调整折线后继续保持正确方向。

## P2：缺少 MCP/外部修改历史视图

事务本身有 label，撤销/重做也保留历史，但网页没有显示事务列表。用户不知道刚才的变化来自人工、网页 Agent 还是 MCP，也看不到每次事务修改了多少元素。

建议增加简洁的历史面板：

- revision；
- 时间；
- 来源（Web、LLM、MCP）；
- transaction label；
- operation 数量；
- 撤销入口。

## P2：MCP 数据库路径配置容易产生“看似成功但网页看不到”

MCP 与网页必须使用同一个 `PID_AGENT_DATABASE_PATH`。如果 MCP 从其他工作目录启动，或设置了不同路径，它可能正常创建和修改另一份数据库，但网页完全看不到。

建议：

- MCP 启动时输出当前数据库的绝对路径；
- 增加 `get_server_info`，返回数据库标识、版本、符号库来源和服务实例信息；
- 网页也显示当前文档存储实例 ID，便于确认双方是否连接同一数据源；
- 文档明确给出网页服务与 MCP 共用数据库的配置示例。

## 4. 建议的产品优先级

### 第一优先级：让外部 Agent 协同过程可见、可理解

1. 网页自动检测外部 revision；
2. MCP 修改后自动刷新当前文档；
3. 超时和连接错误返回清晰信息；
4. 显示事务来源和历史。

这组改进会直接决定用户是否相信“Agent 正在和我共同画图”。

### 第二优先级：补齐高频工程编辑动作

1. 属性面板；
2. 旋转、标签、样式和精确坐标；
3. 原生流向箭头；
4. 交叉线不连接的视觉表达；
5. 更多换热器/冷凝器端口布局。

### 第三优先级：提升 MCP 开发体验

1. 结构化 transaction 参数；
2. `validate_transaction`；
3. 更精确的 operation 错误定位；
4. `get_server_info` 和 schema 工具；
5. 文档订阅或变更事件。

## 5. 推荐的理想协同流程

理想状态下，用户和 Agent 的协作应是：

1. 用户在网页打开文档；
2. Agent 通过 MCP 读取最新 scene summary 和 symbol catalog；
3. Agent 先调用 `validate_transaction`；
4. 校验通过后调用 `apply_transaction`；
5. 网页自动收到 revision 更新并显示新元素；
6. 新增元素短暂高亮，让用户知道 Agent 改了哪里；
7. 用户可直接拖动或修改；
8. Agent 收到新的 revision 后继续下一步；
9. 历史面板保留每次人工和 Agent 操作，可逐步撤销。

如果这一闭环完成，P&ID-Agent 会从“支持 MCP 的绘图工具”真正变成“人和 Agent 同时工作的 P&ID 编辑环境”。

## 6. 本次体验结论

本次实际使用证明了三件事：

1. MCP 确实能够创建具有真实端口和拓扑语义的 P&ID，而不只是生成图片；
2. 当前最大的问题不是文档模型，而是外部修改的可见性和交互反馈；
3. 只要补齐自动同步、错误处理和属性编辑器，现有底座就能支撑更完整的人机协同工作流。

现阶段我会把它定义为：**语义内核和 Agent 接口已经可用，网页协同体验需要优先打磨。**

项目版本：`2.1.0-alpha.1`

测试模型：Ollama `qwen3.6:35b`

## 0. 代码定位与修复结论

2026-07-27 对体验中暴露的问题完成代码复核和修复回归。

确定属于 P&ID-Agent 代码或前后端契约的问题：

- “新建”依赖 `window.prompt()`，导致内嵌浏览器无法创建文档；
- Provider 测试只验证 `/models`，把“能列出模型”误判为“能实际生成”；
- 前端固定允许 600 秒，后端却可能按部署配置静默裁剪到 180 秒；
- 全图语义计划允许 `instrument_tap` 和同位号独立仪表同时存在。

不完全属于代码故障的问题：

- 本地 35B 模型单次规划约需数分钟，这是模型速度与机器资源共同决定的；
- 首稿选错设备、漏接系统边界和冷却空气，是模型遵循复杂提示词不足。应用只能通过更强的提示、结构校验和目标验收降低概率，不能把任意模型输出等同于工程正确。

本次已完成：

- 新建图纸改为应用内对话框；
- Provider 测试在读取模型列表后必做一次真实最小 completion；
- 后端新增运行时超时配置接口，前端显示并限制为服务端有效上限；
- 语义计划拒绝 `instrument_tap` 与同标签独立仪表重复创建，并增强精确设备、边界和 utility connector 提示；
- 在 8001 页面实测 `glm-5.2:cloud` 直接返回无权限，`qwen3.6:35b` 最小生成测试成功。

## 1. 测试目标

在网页中用完整中文工程提示词生成废气冷凝器 P&ID，要求包括：

- 左右系统接口、V-101、V-102 和水平主工艺管线；
- 专用冷凝器 E-101；
- PT-101、TE-101、PT-102、TE-102 四个独立测点；
- 每个测点具有真实 junction、根部隔离阀和细支管；
- 冷却空气从右向左接入冷凝器第二介质端口；
- 全部管线正交、白色背景、深色工程线条和清晰标签。

## 2. 实际操作过程

1. 项目原有服务已运行在 `8000`，前端开发服务运行在 `5174`。
2. 网页“新建”按钮调用原生 `prompt()`，内嵌浏览器不支持，点击后控制台报 `prompt() is not supported`。为了继续测试，仅用项目 REST API 创建空白文档，后续提示词提交、预览、应用和属性编辑均在网页完成。
3. 网页发现 8 个 Ollama 模型。选择 `glm-5.2:cloud` 后，“测试连接”显示成功，但正式生成返回 401，提示 API Key 无效或无模型权限。
4. 改用本地 `qwen3.6:35b`，网页超时输入设为 600 秒，但运行仍在 180 秒失败。检查发现服务启动时的 `PID_AGENT_AGENT_TIMEOUT_SECONDS` 默认是 180，后端会截断前端提交的 600 秒。
5. 为不打断原有服务，在 `8001` 启动同数据库、`PID_AGENT_AGENT_TIMEOUT_SECONDS=600` 的体验实例。重新提交后约 4.5 分钟生成成功，自动应用为 r1、51 个元素。
6. 首稿结构化检查发现：4 个仪表各重复生成一次；设备误选为 `air_cooler`；缺少左右系统接口 connector；冷却空气没有连接到真实端口。
7. 在网页 Agent 手动模式中提交精确修复要求。约 3.5 分钟后得到可审查预览：19 个语义操作、22 个编译操作、预计结果 49 个元素。核对后点击“确认应用”，图纸变为 r2。
8. 100% 放大后发现冷凝器自身长标签与自动 `E-101` 标签重叠。通过网页属性面板把设备标签改为 `E-101`，再选中并删除重复自动文字，形成 r4、48 个元素。
9. 刷新网页后，r4 和 48 个元素完整保留。

## 4. 做得好的地方

### 4.1 预览是真正可审查的工程事务

手动模式不是只展示一张图片，而是明确列出语义操作、编译操作、预计元素数和每个删除、替换、放置、连接动作。对包含删除的修复，系统没有自动应用，而是等待人工确认，这个安全边界合理。

### 4.2 原子性可靠

模型权限失败、180 秒超时和长时间规划期间，空白图纸一直保持 r0/0，没有残留半张图。修复预览期间 r1/51 也没有变化。只有确认事务后 revision 才递增。

### 4.3 端口和 junction 语义可验证

最终能够确认 connector 绑定到具体 `element_id + port_id`，四个仪表 junction 均为真实三通拓扑，冷却空气也确实使用冷凝器第二介质端口。这比“视觉上碰到一起”可靠得多。

### 4.4 属性面板适合做人工收尾

设备标签、位置、尺寸、旋转、颜色和线宽都可以直接编辑。最后的标签重叠不用重新调用模型，通过两次小操作即可修正。

### 4.5 刷新持久化和工程诊断清楚

刷新后 revision 和元素数保持不变；工程报告能返回 0 条诊断。网页状态、文档 API 与报告结果相互一致。

## 5. 主要问题与建议

### P0（已修复）：新建文档依赖原生 `prompt()`

内嵌浏览器不支持 `window.prompt()`，用户点击“新建”后没有可见错误，也无法继续。建议使用应用内模态框或侧边表单，并显示创建失败原因。

### P0（已修复）：模型“测试连接”会产生假阳性

`glm-5.2:cloud` 的模型列表接口可访问，因此测试显示“连接成功，指定模型可用”；真正生成才返回 401。

建议测试连接时增加一次最小 completion，并分别显示：

- 服务可达；
- 模型列表可读；
- 指定模型可完成生成；
- 鉴权有效。

### P0（已修复）：前端 600 秒与后端 180 秒上限不一致

前端允许输入 600 秒，但默认服务把请求截断到 180 秒，用户无法从页面发现这一点。

建议后端把有效最大超时返回给前端，输入框按服务端上限限制；生成开始时显示“本次有效超时 180 秒/600 秒”。

### P1：首稿通过结构校验，但没有通过需求验收

首稿是合法事务，却存在重复仪表、错误设备类型、缺失系统接口和缺失冷却空气 connector。当前“自动完成”更接近“事务合法即成功”，缺少生成后的目标检查。

建议把用户要求编译成可检查约束，在应用前验证：

- 指定 tag 是否唯一；
- 指定 symbol key 或 category 是否满足；
- 必需端口是否已连接；
- 必需 junction 的连接度是否正确；
- 主线是否完整连接到边界；
- 是否存在重复或未连接的仪表。

### P1：长任务进度信息不足

本地 35B 模型单次规划需要数分钟，页面长期只显示“正在规划并编译”，没有耗时、token、有效超时或响应阶段。

建议显示已用时间、有效超时、模型是否仍在输出、当前阶段以及取消后是否会保留预览。

### P1（部分修复）：语义编译会产生重复标签

首稿同时放置显式仪表和带仪表的支路，导致重复符号；替换冷凝器后，设备自身 label 与自动生成的文字 label 又发生重叠。

建议：

- 高级 `add_instrument_branch` 已包含仪表时，检测并拒绝同 tag 的独立 `place_symbol`；
- `replace_symbol` 时避免同时保留长设备 label 和重复自动标签；
- 标签碰撞检测应覆盖符号内部 label、自动 label 和独立 text。

### P2：适应全部后图纸偏小

完整图纸横跨约 1600 个画布单位，右侧面板和左侧图例占用较多宽度，“适应全部”后缩放约 32%，标签阅读性较弱。

建议提供“适应工艺区”“隐藏侧栏后适应”“只适应主流程”等视图动作。

## 6. 总体评价

P&ID-Agent 的结构化文档模型、原子事务、真实端口和人工确认预览是可靠的，已经具备人机共同编辑工程图的核心基础。

当前短板主要在网页工作流和 Agent 完成质量：创建文档的浏览器兼容性、模型测试假阳性、超时配置不透明，以及“事务合法”与“需求满足”之间缺少自动验收。

这次首稿不能直接交付，但通过一次 Agent 修复预览和两次网页属性编辑，最终得到了拓扑正确、诊断为 0、刷新可持久化的图纸。以当前 Alpha 状态看，适合工程人员在场审查和修正，不适合把复杂提示词完全无人值守地一键交付。
